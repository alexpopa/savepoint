# Architecture

## Request flow

```text
Browser -> app/page.tsx -> app/timeline.tsx when signed in
                        |
                        +-> /search when signed out
Browser -> /library -> app/library.tsx (signed in)
Browser -> /search -> public game and player search

Browser UI -> /api/igdb/search, /api/igdb/platforms, and /api/igdb/games/:id -> lib/igdb.ts -> Twitch token + IGDB games/platforms APIs
Browser UI -> /api/players/search -> db/index.ts -> Cloudflare D1
Browser UI -> /api/library      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/library/:id  -> db/index.ts -> Cloudflare D1
Browser UI -> /api/account      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/friends      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/challenges   -> db/index.ts -> Cloudflare D1
Browser -> /search, /users, and /users/:displayName -> db/index.ts -> Cloudflare D1
Browser -> /profile -> db/index.ts -> Cloudflare D1
```

Each library game row on the friends timeline has a clickable game name that opens `app/game-details-dialog.tsx`, loads full IGDB details, and uses the library API to add or remove the viewer's platform copies. The same row includes the **+ Add challenge** action; it opens the shared challenge composer and submits the library owner's account ID and game ID to `POST /api/challenges`, where the API rechecks the friendship and saved game. Challenge timeline rows make the cover and title buttons that open the same `ChallengeDetailsDialog` used on profiles and in collection challenge lists; the feed includes the challenge description and participant profile paths needed by that dialog.

The app uses Next.js App Router components through Vinext, Vite, and the Cloudflare runtime. `app/page.tsx` dynamically reads eligible friend activity through `lib/timeline.ts` and passes serialized entries to `app/timeline.tsx`. `lib/timeline-items.ts` batches each friend’s library additions in backward-looking 24-hour windows before merging challenges and limiting the feed to 30 entries. The page has separate empty and read-error states. No timeline API or activity table is needed. `/library` passes the signed-in identity to the existing collection component in `app/library.tsx`. See [timeline behavior](timeline-design.md) for visibility, grouping, and timestamp rules. In-app route links use native anchors and full document navigation because the current production Vinext bundle fails during client-side link prefetch and navigation; forms and on-page interactions still use client-side React. The shared header in `app/site-header.tsx` submits searches to `/search?q=...` from every app page and displays the RGBoner pixel wordmark, with red R, green G, and blue Boner. Signed-in players get an account icon dropdown containing links for My library (`/library`), My profile, Browse players, and Settings & friends, plus a sign-out form; guests see a direct Sign in link in that area. The search form remains alongside the wordmark and account control. The results page fetches IGDB games and RGBoner players independently, and fetches saved games only for signed-in players; its All, Games, and Players filters keep those result types distinct. The Games heading shows the returned game count. Its platform dropdown has full-row checkbox labels and a client-side search field with a separate X button to clear selected platforms; typing narrows visible choices without changing selections, while checking a platform re-runs only the IGDB game search with repeated platform IDs, filtering for games available on any selected platform before the 30-result limit. The selected platforms remain in repeated `platform` search URL parameters. During a filter request, the prior game cards remain visible but inactive until the replacement results arrive, without refetching player results or navigating the page. Platform choices come from the IGDB platform catalog. A search card opens `app/game-details-dialog.tsx`, which fetches full IGDB details and shows large cover art, screenshots, release information, metadata, and every listed platform. The search card can save directly when only one platform is listed; otherwise platform actions live in the dialog. The library shows the chosen platform on each copy and opens the same dialog when a card is selected. The dialog lists Add or Remove controls for every platform copy, and stays open after a platform is removed so another copy can be added. Other players' library cards open the same dialog and let the viewer manage their own platform copies. The `/users/:displayName` page fetches missing legacy cover art from IGDB in batches and falls back to the saved row when IGDB is unavailable; cover results are cached in the worker isolate for 24 hours. Players include private accounts, library visibility, and the current friendship state, but search responses omit their email addresses and library items. The library component loads saved games and received challenges. `/settings` controls account visibility and friend requests. `/users` lists public accounts and accepted friends. `/users/:displayName` renders another player's library and challenges only after checking public visibility or accepted friendship, and lets a viewer request friendship when needed. Friends can open a centered challenge form on each active library game. `/profile` shows the owner's received challenges in Pending and Completed sections, with favorites first and manual ordering within each section and favorite group; it also shows challenges they created, including older declined submissions. Challenge cards pair the game cover and game title with the challenge title, and link participant names to their profiles. The cover and title buttons open a compact challenge detail dialog with the game cover, challenge title, game context, and description; the cover keeps its aspect ratio, and the participant name sits directly below the title. Within an expanded Challenges list on a collection game, each title-only row has available confirmation and recipient removal controls; clicking the challenge title opens the compact detail dialog with its description. Pending and older Declined profile cards retain their text labels; completed cards use a green left edge without a Completed label. The responsive challenge grid fits as many cards as the available width allows, with one column on mobile. Each participant toggles their own confirmation from a top-right green circle; it fills for that participant and the card turns green only when both confirm. The circle and completion state update in place without a page reload; on the profile, a newly completed challenge moves to Completed immediately. The recipient can favorite challenges and rank them with the arrows shown only on favorites, within each Pending or Completed group; the API rejects reorder requests for non-favorites. Only the challenged player (recipient) can permanently remove a challenge with the top-right X after confirming; there is no separate decline action, and older declined records remain until the recipient removes them. `app/globals.css` contains the shared semantic color tokens and responsive styling for all these screens; [the visual style guide](style-guide.md) sets the design rules for future changes.

When a public-profile cover fails in the browser, the card makes one same-origin, signed-in request to `POST /api/igdb/games/:id/cover`. The server rechecks IGDB, caches that refresh result for 10 minutes per worker isolate, and updates rows whose URL still equals the failed URL or is empty. If IGDB returns the same URL, no cover, or an error, the card falls back without retrying during that page view. For rows with missing legacy artwork, the profile first looks up the saved IGDB ID, then matches the exact title and release year when the stored ID is a legacy fixture value; it uses the resolved catalog ID for the details dialog.

## Authentication and ownership

`app/auth.ts` reads an HTTP-only session cookie, hashes its random token, and looks up an unexpired session in D1. Protected pages redirect unauthenticated visitors to `/login`, and protected APIs return 401. `/search` and its game and player search APIs are public. Header sign-in uses the default login destination `/`; after authentication, `/` renders the signed-in player's recent activity timeline. Login flows that explicitly request a safe return path can still return to that destination. `POST /api/auth/register` creates a pending account with a salted PBKDF2-SHA-256 password hash using 100,000 iterations, the maximum supported by the Worker runtime, and emails a 24-hour verification link. The same setting is used when verifying passwords and resetting them. The link opens a confirmation page; a same-origin POST consumes its hashed, single-use token and then issues a session. Registration failures log the server-side exception stack with `console.error` before returning a generic 503 response; the exception details are not sent to the browser. In production, inspect these entries with the Sites production Worker log reader. Unverified accounts cannot sign in, appear in player search, or receive friend requests. `POST /api/auth/login` verifies the password and issues a 30-day session. It limits failed attempts for each email address to 10 per 15-minute window. `POST /api/auth/logout` revokes that session and clears the cookie. A reset request emails a 30-minute link; using it changes the password and revokes all existing sessions. Link requests are limited to one per account and purpose per minute, and reset responses do not reveal whether an account exists. The cookie uses `SameSite=Lax`, `HttpOnly`, and `Secure` on HTTPS. Passwords and raw session tokens are never stored in D1.

The email and case-insensitive display-name indexes apply only to rows with a password hash. The display-name index uses SQLite `lower()`, which folds ASCII letters. Registration rejects duplicate names, including names reserved by unverified email accounts, and rejects names that cannot safely be used as one URL segment. Older ChatGPT-based account rows remain in D1, but they cannot sign in and are excluded from player search, profiles, and friend requests. A fresh email account may use the same address without inheriting old data. `lib/auth-email.ts` sends verification and reset links through the Resend HTTP API, using server-side `RESEND_API_KEY`, `AUTH_EMAIL_FROM`, and `AUTH_PUBLIC_URL`. Local console delivery works only for localhost. The local Vite plugin no longer simulates ChatGPT identity.

Every owner library query includes the authenticated `userId`. Deletes match both the row ID and user ID. Other players' libraries and challenges are read by the server-rendered `/users/:displayName` page after an account visibility and friendship check; the display name is URL encoded, and existing UUID profile links redirect to it. Accounts whose stored name equals their email retain their UUID profile link so the link does not expose their email. The resolved account's `userId` remains the internal key for friendship, library, and challenge queries. There is no separate unguarded public library or challenge API. Private is the database default. Pending requests do not grant access, and removing a friendship immediately revokes profile access on subsequent requests. Challenge creation requires an accepted friendship and an active library entry, even when the recipient's profile is public. Only the creator and recipient may change their own completion confirmations. Only the challenged player (recipient) may permanently remove a challenge; only the recipient may favorite a challenge or rank one that is currently favorited. Older declined records remain visible to the creator until the recipient removes them, but there is no separate decline action for new challenges. Participants retain confirmation access through their own profile after a friendship ends or a game is removed. Write endpoints call `lib/request-security.ts` to reject a mismatched `Origin` header when one is present. Login return paths are limited to relative app paths.

## API

| Route | Behavior |
| --- | --- |
| `POST /api/auth/register` | Create a pending email account with a unique display name and send a verification link; duplicate names or emails return 409, and no session is issued until verification. Same-origin write. |
| `POST /api/auth/login` | Verify email and password and issue a session. Same-origin write. |
| `POST /api/auth/verify` | Consume a single-use verification token and issue a session. Same-origin write. |
| `POST /api/auth/resend-verification` | Send a new link for an unverified account, at most once per minute. Same-origin write. |
| `POST /api/auth/request-reset` | Send a password reset link for a verified account, at most once per minute. Same-origin write. |
| `POST /api/auth/reset-password` | Consume a single-use token, change the password, and revoke sessions. Same-origin write. |
| `POST /api/auth/logout` | Revoke the current session and clear the cookie. Same-origin write. |
| `GET /api/igdb/search?q=...&platform=...&platform=...` | Public IGDB search for 2–100 character queries; repeated positive IGDB platform IDs filter for games available on any selected platform before returning up to 30 serialized results. |
| `GET /api/igdb/platforms` | Public IGDB platform catalog for the search filter; the server caches the catalog in memory for 24 hours and the response can be cached for a day. |
| `GET /api/igdb/games/:id` | Public detail lookup for one IGDB game, including release date, summary, storyline, platforms, genres, modes, themes, perspectives, companies, rating, and screenshots when available. |
| `POST /api/igdb/games/:id/cover` | Accept `{ "failedCoverUrl": string }`, fetch the current IGDB cover, and refresh matching rows whose saved cover URL still equals the failed URL or is empty. Requires sign-in and same-origin write. |
| `GET /api/players/search?q=...` | Search existing RGBoner accounts by display name or email text for 2–100 character queries; return up to 30 other players with display label, profile path, library visibility, and friendship state. Private accounts are included, but email addresses and library items are omitted. Visitors can match display names; email-text matching and friendship state require sign-in. |
| `GET /api/library` | Return the current user's saved games, newest first. Requires sign-in. |
| `POST /api/library` | Accept `{ "igdbId": number, "platformId": number }`, validate the platform against fresh IGDB data, and save a game/platform copy. The platform ID may be omitted for a game with exactly one listed platform; use `0` when IGDB lists none. Duplicate copies return 409. Requires sign-in and same-origin write. |
| `PATCH /api/library/:id` | Accept `{ "platformId": number }` to change a saved copy's platform after validation against IGDB. An already-owned platform returns 409. Requires ownership, sign-in, and same-origin write. |
| `DELETE /api/library/:id` | Remove one saved row belonging to the current user. Requires sign-in and same-origin write. |
| `GET /api/account` | Return the signed-in user's account visibility and friend/request lists. Accounts are created at registration with private visibility. |
| `PATCH /api/account` | Accept `{ "isPublic": boolean }` to update only the current user's library visibility. Requires sign-in and same-origin write. |
| `GET /api/friends` | Return accepted friendships and pending incoming/outgoing requests. Requires sign-in. |
| `POST /api/friends` | Accept `{ "email": string }` or `{ "userId": string }` to request friendship with an existing RGBoner account. The latter supports search results and profiles without exposing the target email. Requires sign-in and same-origin write. |
| `PATCH /api/friends/:userId` | Accept `{ "action": "accept" }` for an incoming pending request. Requires sign-in and same-origin write. |
| `DELETE /api/friends/:userId` | Decline or cancel a pending request, or remove an accepted friendship. Requires sign-in and same-origin write. |
| `GET /api/challenges?scope=received\|sent` | Return only the signed-in player's received active challenges or created challenges, including older records previously declined by recipients. Requires sign-in. |
| `POST /api/challenges` | Accept `{ "recipientId": string, "igdbId": number, "title": string, "description": string }`; require an accepted friendship and that the recipient currently has the game saved. Requires sign-in and same-origin write. |
| `PATCH /api/challenges/:id` | Accept `confirm`, `unconfirm`, `favorite`, `unfavorite`, `move_up`, or `move_down`. A participant changes only their own confirmation; only the recipient can favorite a challenge or rank a favorited one. Requires sign-in and same-origin write. |
| `DELETE /api/challenges/:id` | Permanently remove a challenge, including older declined records. Only the challenged player (recipient) can remove it. Requires sign-in and same-origin write. |

Search, library, account, friend, and challenge GET responses use `Cache-Control: private, no-store`; the public platform catalog uses one-day caching. The search page and read-only IGDB and player search APIs allow guests; write endpoints for saved games and friendships still require a session. The browser never supplies the stored name, cover, year, or platform name: library writes load and validate those values from IGDB using submitted IDs. Challenge creation snapshots the name and cover from the recipient's saved game. Challenges are keyed to the IGDB game, so a game saved on several platforms shows the same challenge list on each copy. Game and player search load separately so one source can still display results if the other fails. A fallback account display label uses the part before `@` rather than returning an email address in player search or profiles.

## External data and storage

`lib/igdb.ts` gets a Twitch client-credentials token using `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET`, caches it in server memory until near expiry, and calls the IGDB games and platforms APIs. The platform catalog is cached in server memory for 24 hours. Game search applies an optional list of platform IDs in IGDB before its 30-result limit; the parenthesized IGDB filter returns games available on any selected platform. It converts IGDB image IDs into image URLs and release timestamps into UTC dates and years. Search fetches compact cards; the game detail endpoint fetches richer metadata. Credentials stay server-side. Search results are transient; saved records hold a snapshot of basic IGDB details, so they do not update automatically when IGDB changes.

`db/schema.ts` defines `library_items`, `accounts`, `sessions`, `login_attempts`, `auth_tokens`, `friendships`, and `challenges` in SQLite/D1. Account emails are normalized to lowercase for friend-request lookup, display names are unique among email accounts under SQLite ASCII case folding, and public visibility defaults to false. A friendship row stores an ordered user pair, the requester, and `pending` or `accepted` status. A challenge is keyed to recipient and IGDB game rather than to a removable library row. Its game snapshot keeps historical entries readable after removal; if the game is saved again, its challenge list reappears. Challenge cards prefer the current saved library cover for the linked IGDB game, then the challenge's saved cover snapshot; when both are missing, challenge lists attempt the same IGDB artwork recovery used for legacy profile covers. The challenge is completed only while both confirmation flags are true. Either participant can undo their own confirmation. The nullable `timeline_at` stores the time of the latest visible state transition, updated atomically with confirmation flags; creator-only confirmation, favorites, ranking, and repeated no-op confirmations leave it unchanged. New challenges initialize it to creation time; pre-migration challenges remain excluded until a visible transition. Older records with a recipient decline timestamp remain visible to the creator under Declined for compatibility; new challenges have no decline action, and only the challenged player can permanently remove a challenge. Challenges store a title and description; profile cards omit the description, and their detail dialog displays it on demand. The library stores one entry per IGDB game and selected platform; `platforms_json` remains catalog metadata. Existing rows migrated from the earlier one-game model have platform ID `0` and can be edited to a listed IGDB platform. `db/index.ts` obtains the `DB` Cloudflare binding and creates a Drizzle client. Drizzle migrations live in `drizzle/`; apply `0000` through `0008` on an empty database, or only unapplied migrations on an existing database. `.openai/hosting.json` declares the D1 binding name, while `vite.config.ts` supplies a local D1 binding for development.

## Where to make changes

| Change | Start with |
| --- | --- |
| Page layout or interaction | `app/site-header.tsx`, `app/search/`, `app/library.tsx`, `app/globals.css` |
| API behavior | `app/api/` and its helpers in `lib/` |
| Identity or redirects | `app/auth.ts`, `app/login/`, and `app/api/auth/` |
| Stored fields | `db/schema.ts`, `drizzle/`, and library API serialization |
| Runtime bindings or build | `.openai/hosting.json`, `vite.config.ts`, `scripts/` |
