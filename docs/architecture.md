# Architecture

## Request flow

```text
Browser -> app/page.tsx -> app/timeline.tsx when signed in
                        |
                        +-> /search when signed out
Browser -> /library -> app/library.tsx (signed in)
Browser -> /search -> public game and player search
Browser -> /search without a term -> recent library popularity query -> Cloudflare D1

Browser UI -> /api/igdb/search, /api/igdb/platforms, and /api/igdb/games/:id -> lib/igdb.ts -> Twitch token + IGDB games/platforms APIs
Browser UI -> /api/players/search -> db/index.ts -> Cloudflare D1
Browser UI -> /api/library      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/library/:id  -> db/index.ts -> Cloudflare D1
Browser UI -> /api/account      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/friends      -> db/index.ts -> Cloudflare D1
Browser UI -> /api/challenges   -> db/index.ts -> Cloudflare D1
Browser -> /search, /users, and /users/:displayName -> db/index.ts -> Cloudflare D1
Browser -> /profile -> db/index.ts -> Cloudflare D1
Browser -> /messages and /messages/:displayName -> lib/messages.ts -> Cloudflare D1
Browser UI -> /api/messages -> lib/messages.ts -> Cloudflare D1
```

Each library game row on the friends timeline has a clickable game name that opens `app/game-details-dialog.tsx`, loads full IGDB details, and uses the library API to add or remove the viewer's platform copies. Library batches initially show four copies and reveal 12 more per click, up to 100; the server sends at most 100 game snapshots with the full batch count, and larger batches end with a link to the player’s Library section. The same row includes the **+ Add challenge** action; it opens the shared challenge composer and submits the library owner's account ID and game ID to `POST /api/challenges`, where the API rechecks the friendship and saved game. Challenge timeline rows make the cover and title buttons that open the same `ChallengeDetailsDialog` used on profiles and in collection challenge lists; the feed includes the challenge description and participant profile paths needed by that dialog.

The app uses Next.js App Router components through Vinext, Vite, and the Cloudflare runtime. `app/page.tsx` dynamically reads eligible friend activity through `lib/timeline.ts` and passes serialized entries to `app/timeline.tsx`. `lib/timeline-items.ts` batches each friend’s library additions in backward-looking 24-hour windows before merging challenges and taking a page of 15 entries. Each source is read newest first with a limit, starting from the viewer's accepted friends, and all twelve reads go to D1 in one batch (`lib/timeline-queries.ts`); the private `GET /api/timeline?cursor=…` returns later pages for the **Show more** button. The page has separate empty and read-error states. No activity table is needed. `/library` passes the signed-in identity to the existing collection component in `app/library.tsx`. See [timeline behavior](timeline-design.md) for visibility, grouping, and timestamp rules. In-app route links use native anchors and full document navigation because the current production Vinext bundle fails during client-side link prefetch and navigation; forms and on-page interactions still use client-side React. The shared header in `app/site-header.tsx` submits searches to `/search?q=...` from every app page and displays the RGBoner pixel wordmark, with red R, green G, and blue Boner. Signed-in players get an account icon dropdown containing links for My library (`/library`), My profile, Browse players, Connected libraries (`/connections`), and Settings & friends, plus a sign-out form; guests see a direct Sign in link in that area. Signed-in headers load the incoming friend-request count from private `GET /api/friends/pending-count` and show it beside the account icon and Settings & friends only when the count is nonzero. A message icon to the left of the account icon links to `/messages` and shows the unread message count the same way; see [Messages](#messages). The search form remains alongside the wordmark and account control. On `/search` without a term, the server reads current library additions from the last 14 days, ranks IGDB games by distinct player count, and sends at most six cards to the client. Ties use the latest add and then IGDB ID. These cards reuse the library’s compact horizontal game-card styling, showing the cover, title, year, and muted player count without the library’s Challenges area. They open the shared game detail dialog and expose only aggregate counts and stored game snapshots, never player identities. If no games qualify or the read fails, the page shows an appropriate empty or error state. The results page fetches IGDB games and RGBoner players independently, and fetches saved games only for signed-in players; its All, Games, and Players filters keep those result types distinct. The Games heading shows the returned game count. Its platform dropdown has full-row checkbox labels and a client-side search field with a separate X button to clear selected platforms; typing narrows visible choices without changing selections, while checking a platform re-runs only the IGDB game search with repeated platform IDs, filtering for games available on any selected platform before the 30-result limit. The selected platforms remain in repeated `platform` search URL parameters. During a filter request, the prior game cards remain visible but inactive until the replacement results arrive, without refetching player results or navigating the page. Platform choices come from the IGDB platform catalog. A search card opens `app/game-details-dialog.tsx`, which fetches full IGDB details and shows large cover art, screenshots, release information, metadata, and every listed platform. The search card can save directly when only one platform is listed; otherwise platform actions live in the dialog. The library shows the chosen platform on each copy and opens the same dialog when a card is selected. The dialog lists Add or Remove controls for every platform copy, and stays open after a platform is removed so another copy can be added. Other players' library cards open the same dialog and let the viewer manage their own platform copies. The `/users/:displayName` page fetches missing legacy cover art from IGDB in batches and falls back to the saved row when IGDB is unavailable; cover results are cached in the worker isolate for 24 hours. Players include private accounts, library visibility, and the current friendship state, but search responses omit their email addresses and library items. The library component loads saved games and received challenges. `/settings` controls account visibility and friend requests. `/connections` is the signed-in connected-library overview: a separate card for Steam, Xbox, PlayStation, and RetroAchievements, in a two-column grid, reads only the current player’s connection status and Xbox, PlayStation, or RetroAchievements display name, shows Connect or Manage, and flags PlayStation reconnection when needed. A read failure shows an alert and keeps service links available. Existing `/settings/steam`, `/settings/xbox`, `/settings/playstation`, and `/settings/retroachievements` routes retain their connection workflows and link back to this overview. `/users` lists public accounts and accepted friends for regular players, and all verified accounts for admins. `/users/:displayName` renders another player's library and challenges only after checking public visibility, accepted friendship, or the viewer's admin permission, and lets a viewer request friendship when needed. Friends and admins can open a centered challenge form on each active library game. Both profile routes share one layout with no explanatory copy. `app/profile-nameplate.tsx` renders the nameplate: for a profile the viewer can see, the cover of the player's #1 favorite as its portrait avatar; when there is no favorite, its cover is absent or fails to load, or the profile is locked, a mirrored pixel avatar derived from the account ID (nothing new is stored). It also shows the display name, a visibility chip (Private or Public for the owner, linking to `/settings`; Friend, Public, or Private for others, reflecting real friendship and visibility, never the viewer's role), and counters for distinct saved games, cleared challenges, and pending challenges. `/profile` reads its account visibility, received and sent challenges, Top 10, currently playing copies, and distinct saved and completed game counts in one D1 batch (`getOwnProfile` in `lib/profile.ts`), so the page makes one database round trip after the session lookup; `/users/:displayName` derives its counters from rows it already loads after the visibility check. `HallOfHonor` in `app/challenges.tsx` renders directly below Currently playing: the recipient's starred completed challenges, in their saved order, as covers in a wooden-cabinet frame. Like the Top 10, a caption below the cabinet shows the hovered or focused challenge's title, and each cover opens the detail popup with the game, challenger, and description. At most six challenges can be starred (`honorLimit` in `lib/challenge-queries.ts`); an atomic conditional update checks the count and completion and appends the new honor in the same statement, and the recipient or an admin reorders them with Edit, picking a challenge up and setting it down like the Top 10. Placement is atomic, shifts the honors in between, and renumbers them so legacy rows that share an order still move. Owners see the vacant places, or, before they have completed any challenge, a note in place of the cabinet. `ProfileChallenges` renders a tabbed log below the Top 10: Pending and Completed received challenges, leaving out those already in the Hall of Honor, plus a Sent tab on `/profile` for challenges the owner created, including older declined submissions. Whenever the log has any challenges, a search field matches the game, challenge title, or either player's name (`filterChallenges` in `lib/challenge-log.ts`); each tab shows six matches at a time with a **Show more** button. Confirmation changes update both lists in place. Challenge cards pair the game cover and game title with the challenge title, and link participant names to their profiles. The cover and title buttons open a compact challenge detail dialog with the game cover, challenge title, game context, and description; the cover keeps its aspect ratio, and the participant name sits directly below the title. Within an expanded Challenges list on a collection game, each title-only row has available confirmation and recipient removal controls; clicking the challenge title opens the compact detail dialog with its description. Pending and older Declined profile cards retain their text labels; completed cards use a green left edge without a Completed label. The responsive challenge grid fits as many cards as the available width allows, with one column on mobile. Each participant toggles their own confirmation from a top-right green circle; it fills for that participant and the card turns green only when both confirm. The circle and completion state update in place without a page reload; on the profile, a newly completed challenge moves to Completed immediately. The recipient can favorite challenges and rank them with the arrows shown only on favorites, within each Pending or Completed group; the API rejects reorder requests for non-favorites. The challenged player (recipient) or an admin can permanently remove a challenge with the top-right X after confirming; there is no separate decline action, and older declined records remain until the recipient removes it. `app/globals.css` contains the shared semantic color tokens and responsive styling for all these screens; [the visual style guide](style-guide.md) sets the design rules for future changes.

When a public-profile cover fails in the browser, the card makes one same-origin, signed-in request to `POST /api/igdb/games/:id/cover`. The server rechecks IGDB, caches that refresh result for 10 minutes per worker isolate, and updates rows whose URL still equals the failed URL or is empty. If IGDB returns the same URL, no cover, or an error, the card falls back without retrying during that page view. For rows with missing legacy artwork, the profile first looks up the saved IGDB ID, then matches the exact title and release year when the stored ID is a legacy fixture value; it uses the resolved catalog ID for the details dialog. Idle search uses the same cached recovery for its at most six popular games when stored covers are missing; the D1 ranking is complete before that optional IGDB work.

## My library

`app/library.tsx` shows the signed-in viewer's saved platform copies, newest first by default, with at most 12 cards on a page. A **Sort** select also offers Highest rated and Completed first (`sortLibraryGames` in `lib/library-view.ts`); ties keep the newest-first order. A game-title search and the shared `app/platform-filter.tsx` dropdown narrow the collection together: selected platform IDs match any chosen platform, and the dropdown's own search narrows only its checkbox options without changing the selection. The filter offers a separate clear-selection control. Changing the title or platforms returns to the first page. The collection shows the visible result range, total matches, and page controls; when filters have no matches, it shows a specific empty state instead of the empty-library prompt. The library count still represents all saved platform copies. Opening a card keeps all of that game's owned platform copies available to the game details dialog, including copies on other pages.

On another player's profile, `app/users/[userId]/public-library.tsx` applies the same title search, searchable platform filter, sort select, 12-copy pagination, visible range, and no-match state to the profile copies already loaded after the profile visibility check. Opening a card still keeps the viewer's own platform copies available in the game details dialog.

## Authentication and ownership

`app/auth.ts` reads an HTTP-only session cookie, hashes its random token, and looks up an unexpired session in D1. Protected pages redirect unauthenticated visitors to `/login`, and protected APIs return 401. `/search`, `/users/:displayName`, and the game and player search APIs accept guests; the profile route loads private content only for authorized viewers. Header sign-in uses the default login destination `/`; after authentication, `/` renders the signed-in player's recent activity timeline. Login flows that explicitly request a safe return path can still return to that destination. `POST /api/auth/register` creates a pending account with a salted PBKDF2-SHA-256 password hash using 100,000 iterations, the maximum supported by the Worker runtime, and emails a 24-hour verification link. The same setting is used when verifying passwords and resetting them. The link opens a confirmation page; a same-origin POST consumes its hashed, single-use token and then issues a session. Registration failures log the server-side exception stack with `console.error` before returning a generic 503 response; the exception details are not sent to the browser. In production, inspect these entries with the Sites production Worker log reader. Unverified accounts cannot sign in, appear in player search, or receive friend requests. `POST /api/auth/login` verifies the password and issues a 30-day session. It limits failed attempts for each email address to 10 per 15-minute window. `POST /api/auth/logout` revokes that session and clears the cookie. A reset request emails a 30-minute link; using it changes the password and revokes all existing sessions. Link requests are limited to one per account and purpose per minute, and reset responses do not reveal whether an account exists. The cookie uses `SameSite=Lax`, `HttpOnly`, and `Secure` on HTTPS. Passwords and raw session tokens are never stored in D1.

The email and case-insensitive display-name indexes apply only to rows with a password hash. The display-name index uses SQLite `lower()`, which folds ASCII letters. Registration rejects duplicate names, including names reserved by unverified email accounts, and rejects names that cannot safely be used as one URL segment. Older ChatGPT-based account rows remain in D1, but they cannot sign in and are excluded from player search, profiles, and friend requests. A fresh email account may use the same address without inheriting old data. `lib/auth-email.ts` issues verification and reset tokens and sends their links through `lib/email.ts`, which calls the Resend HTTP API using server-side `RESEND_API_KEY` and `AUTH_EMAIL_FROM`; links use `AUTH_PUBLIC_URL`. Local console delivery works only for localhost. See [conventions](conventions.md#email) for adding other emails. The local Vite plugin no longer simulates ChatGPT identity.

The personal library list and add endpoints use the authenticated `userId`. Library edits and deletes match both the row ID and user ID for regular players; admins may edit or delete any row by ID, with platform uniqueness checked against its actual owner. Other players' libraries and challenges are read by the server-rendered `/users/:displayName` page after an account visibility and friendship check. A public profile exposes its currently playing games, Top 10, Hall of Honor, challenges, and library to signed-out visitors, including game and challenge details. Guests cannot edit a profile, add a friend, or use personal library controls. Every guest profile shows a login link that returns to the same profile to request friendship. A signed-in non-friend sees a request button, an incoming request can be accepted there, and an outgoing request shows its pending state. Private profiles show only a nameplate and Friends only state to guests. The display name is URL encoded, and existing UUID profile links redirect to it. Accounts whose stored name equals their email retain their UUID profile link so the link does not expose their email. The resolved account's `userId` remains the internal key for friendship, library, and challenge queries. There is no separate unguarded public library or challenge API. Private is the database default. Pending requests do not grant regular players access, and removing a friendship immediately revokes their private-profile access on subsequent requests. Admin access is independent of friendships. Challenge creation requires an accepted friendship for regular players and an active library entry for every player, even when the recipient's profile is public. Admins may create challenges without friendship. Regular players may change only their own completion confirmations; admins may change either participant's confirmation. Regular players may permanently remove, favorite, or rank received challenges only as the recipient. Admins may perform those actions on any challenge. Ranking still requires a favorite and stays within the recipient's completion group. Older declined records remain visible to the creator until the recipient removes them, but there is no separate decline action for new challenges. Participants retain confirmation access through their own profile after a friendship ends or a game is removed. Write endpoints call `lib/request-security.ts` to reject a mismatched `Origin` header when one is present. Login return paths are limited to relative app paths.

## Roles and permissions

The app has admins and regular players. `account_roles` contains only grants with `role = 'admin'`, keyed by `accounts.user_id`; an absent row means a regular player. `app/auth.ts` joins the role to a valid, unexpired session and a verified email account on every request. Its `AppUser.isAdmin` is a server-derived property of the current viewer. It is never accepted from clients, inferred from an email, cached into a session, or attached to another player's public data.

**Admins have every application permission.** All new page and API authorization must use `hasPermission(user, ordinarilyAllowed)` from `lib/permissions.ts`, or a helper built on it, so admins always bypass ordinary ownership, friendship, visibility, and participant restrictions. Use `canViewProfile` for profile privacy. Extend this central policy when adding features instead of scattering role comparisons. Authentication, same-origin writes, valid inputs, verified account eligibility, existing resources, and database integrity remain mandatory. Admin status does not make expired sessions valid or permit invalid platform copies, self-challenges, or nonexistent resources.

Current admin behavior:

- View any verified player's library and challenges, including a private profile without friendship. Browse players includes all verified accounts for an admin.
- Keep the ordinary Add friend, incoming request, outgoing request, and accepted friendship behavior. Viewing private data neither creates nor accepts a friendship; private profiles remain labeled private until there is a real friendship. Admins still send requests normally and the other player accepts them normally.
- Create a challenge for another verified player's saved game without friendship; confirm or undo either participant, add or remove Hall of Honor challenges and reorder them for that recipient, and remove any challenge. Admin viewers get the corresponding existing controls on profiles. Confirmation requests may explicitly select `participant: "creator"` or `"recipient"`; a regular player can select only their own participant, while an admin can select either. Without this field, a creator changes the creator flag and other authorized viewers change the recipient flag.
- Edit or delete any library item by its ID. A platform edit uses the item's real owner for duplicate checks and preserves that ownership.
- Keep the home timeline scoped to actual friends; its participant privacy checks allow an admin to see a friend's activity involving a private non-friend. Role access does not subscribe the admin to every player's activity.

Personal endpoints and pages still mean the current viewer's own account, library, friends, received challenges, and sent challenges. An admin role does not silently impersonate a profile owner or change the destination of an Add game action. Resource-specific endpoints enforce the admin override when a different resource is explicitly targeted.

Direct messages are the one deliberate exception to the admin override: sending and reading a conversation require an accepted friendship for admins too, because a message from a non-friend would reveal the sender's role, and admins cannot read other players' conversations. See [Messages](#messages).

Admin-only pages may offer additional permitted actions or data (see [Admin portal](#admin-portal)), but regular players must never see who is an admin. Do not add badges, colors, labels, role directories, or role fields to profile, search, account, friendship, or challenge responses. Links to admin-only pages render only for the admin viewing them. Pass only the current viewer's required action capabilities to client components, never a target account's role or the full `AppUser`. Client flags render controls only; the API independently rechecks permission from its authenticated session. There is no UI or HTTP API for adding or removing admins. Role changes are explicitly authorized, trusted D1 operations; see [development](development.md#roles-and-trusted-administration).

Migration `0010_user_roles.sql` creates the table and includes the specifically requested one-time grant for the confirmed existing production owner account. Registration and login contain no email-based admin bootstrap. Grants and revocations take effect on the next request, including within an existing session. Player privacy preferences, friendships, and role grants are independent records. This application role is also separate from the Sites owner/editor/viewer sharing roles and the Site's public audience.

### Admin portal

`/admin` (`app/admin/page.tsx`) is a server-rendered site overview for admins. It checks `hasPermission(user, false)` and calls `notFound()` for guests and regular players, so they get the ordinary 404 and cannot tell the page exists. It reads aggregate counts in one D1 statement (`siteStatsQuery` in `lib/admin-queries.ts`, loaded by `getSiteStats` in `lib/admin.ts`):

- Players: verified email accounts, public profiles among them, accounts awaiting email verification, and distinct accounts with an unexpired session. ChatGPT-era records without a password are not counted.
- Libraries: distinct IGDB games, saved platform copies, currently playing and completed copies, Top 10 favorites, and scores.
- Social: challenges, cleared challenges (both confirmations), accepted friendships, and pending friend requests.
- Last 7 days: library copies added, challenges created, games scored, and friend requests sent, by their stored timestamps. Accounts have no creation time, so there is no signup count.

The page shows only totals: no emails, roles, or per-player rows. If the read fails it shows an inline error. Signed-in pages pass `showAdmin={hasPermission(user, false)}` to `SiteHeader` (through `Library`, `Timeline`, and `Settings` for client pages), which adds an **Admin** item to the account menu only for admins. The portal has no write actions and no role management; it is not a timeline source. Add new admin views as sections of this page or as routes under `/admin/` with the same `notFound()` check, and put any admin write through a normal API route that rechecks `hasPermission` on the server.

## API

| Route | Behavior |
| --- | --- |
| `POST /api/auth/register` | Create a pending email account with a unique display name and send a verification link; duplicate names or emails return 409, and no session is issued until verification. Same-origin write. |
| `POST /api/auth/login` | Verify email and password and issue a session. Same-origin write. |
| `POST /api/auth/verify` | Consume a single-use verification token and issue a session. Same-origin write. |
| `POST /api/auth/resend-verification` | Send a new link for an unverified account, at most once per minute. Same-origin write. |
| `POST /api/auth/request-reset` | Send a password reset link for a verified account, at most once per minute. Same-origin write. |
| `POST /api/auth/reset-password` | Consume a single-use token, change the password, and revoke sessions. Same-origin write. |
| `POST /api/auth/logout` | Revoke the current session and clear the cookie. Same-origin write. |
| `GET /api/igdb/search?q=...&platform=...&platform=...` | Public IGDB search for 2–100 character queries; repeated positive IGDB platform IDs filter for games available on any selected platform before returning up to 30 serialized results. |
| `GET /api/igdb/platforms` | Public IGDB platform catalog for the search filter; the server caches the catalog in memory for 24 hours and the response can be cached for a day. |
| `GET /api/igdb/games/:id` | Public detail lookup for one IGDB game, including release date, summary, storyline, platforms, genres, modes, themes, perspectives, companies, rating, and screenshots when available. |
| `POST /api/igdb/games/:id/cover` | Accept `{ "failedCoverUrl": string }`, fetch the current IGDB cover, and refresh matching rows whose saved cover URL still equals the failed URL or is empty. Requires sign-in and same-origin write. |
| `GET /api/players/search?q=...` | Search existing RGBoner accounts by display name or email text for 2–100 character queries; return up to 30 other players with display label, profile path, library visibility, and friendship state. Private accounts are included, but email addresses and library items are omitted. Visitors can match display names; email-text matching and friendship state require sign-in. |
| `GET /api/library` | Return the current user's saved games, newest first, each with its `completedAt` and the user's `score` for that game. Requires sign-in. |
| `POST /api/library` | Accept `{ "igdbId": number, "platformId": number }`, validate the platform against fresh IGDB data, and save a game/platform copy. The platform ID may be omitted for a game with exactly one listed platform; use `0` when IGDB lists none. Duplicate copies return 409. Requires sign-in and same-origin write. |
| `PATCH /api/library/:id` | Accept `{ "platformId": number }` to change a saved copy's platform after validation against IGDB. An already-owned platform returns 409. Requires ownership or admin permission, sign-in, and same-origin write. |
| `DELETE /api/library/:id` | Remove one saved row belonging to the current user, or any row by ID for an admin. Requires sign-in and same-origin write. |
| `PUT /api/library/:id/playing` | Mark one saved platform copy as currently playing and return the owner's currently playing list. Repeating the request keeps the original `playing_since`. Requires ownership or admin permission, sign-in, and same-origin write. |
| `DELETE /api/library/:id/playing` | Clear the currently playing mark and return the owner's list. Same permissions as `PUT`. |
| `PUT /api/library/:id/completed` | Mark one saved platform copy completed and return `{ completedAt }`. Repeating the request keeps the original `completed_at`. Currently playing is unchanged. Requires ownership or admin permission, sign-in, and same-origin write. |
| `DELETE /api/library/:id/completed` | Clear the completed mark and return `{ completedAt: null }`. Same permissions as `PUT`. |
| `GET /api/library/copies` | Return `items`: ten of the signed-in viewer's own platform copies (ID, IGDB ID, name, cover, platform), newest first, plus a `next` cursor when more exist. With `group=game`, return one row per game instead (ID and IGDB ID are the IGDB ID, the name and cover come from the newest copy, and `platformNames` joins the matching platforms), keyed by that game's newest copy. Optional `q` matches a literal, case-insensitive substring of the title (`%`, `_`, and `\` are escaped); repeated `platform` parameters (up to 50) match copies on any of those IGDB platform IDs (`0` for “Platform not set”); `cursor` continues from the previous page using keyset pagination on `(added_at, id)`. The first page of copies also returns the viewer's distinct platforms for the filter. Malformed parameters return 400. Private, uncached response. The SQL lives in `lib/library-copies-query.ts`. |
| `GET /api/account` | Return the signed-in user's account visibility and friend/request lists. Accounts are created at registration with private visibility. |
| `PATCH /api/account` | Accept `{ "isPublic": boolean }` to update only the current user's library visibility. Requires sign-in and same-origin write. |
| `GET /api/friends` | Return accepted friendships and pending incoming/outgoing requests. Requires sign-in. |
| `POST /api/friends` | Accept `{ "email": string }` or `{ "userId": string }` to request friendship with an existing RGBoner account. The latter supports search results and profiles without exposing the target email. After the request is saved, the recipient gets an email naming the requester by display name, with links to `/settings` to accept or decline and to the requester's profile; a delivery failure is logged and does not fail the request. Requires sign-in and same-origin write. |
| `PATCH /api/friends/:userId` | Accept `{ "action": "accept" }` for an incoming pending request. Requires sign-in and same-origin write. |
| `DELETE /api/friends/:userId` | Decline or cancel a pending request, or remove an accepted friendship. Requires sign-in and same-origin write. |
| `GET /api/challenges?scope=received\|sent` | Return only the signed-in player's received active challenges or created challenges, including older records previously declined by recipients. Requires sign-in. |
| `POST /api/challenges` | Accept `{ "recipientId": string, "igdbId": number, "title": string, "description": string }`; require an accepted friendship or admin permission and that the recipient currently has the game saved. Requires sign-in and same-origin write. |
| `PATCH /api/challenges/:id` | Accept `confirm`, `unconfirm`, `favorite`, `unfavorite`, or `place` with `{ position: 1–6 }`. A regular participant changes only their own confirmation; only a regular recipient can favorite (add to the Hall of Honor) or rank. Admins can select either confirmation and manage any challenge. Favoriting requires a completed challenge and returns 409 when six are already starred; `place` moves a Hall of Honor challenge to that position against current database order, clamped to the last honor. Requires sign-in and same-origin write. |
| `DELETE /api/challenges/:id` | Permanently remove a challenge, including older declined records. The challenged player (recipient) or an admin can remove it. Requires sign-in and same-origin write. |
| `GET /api/timeline?cursor=...` | Return `{ items, next }`: the signed-in player's next 15 friend timeline entries after the `next` cursor from the previous page (the home page renders the first page). Returns 400 for a malformed cursor. See [timeline pages](timeline-design.md#pages). |

Search, library, account, friend, challenge, and timeline GET responses use `Cache-Control: private, no-store`; the public platform catalog uses one-day caching. The search page, public profile pages, and read-only IGDB and player search APIs allow guests; write endpoints for saved games and friendships still require a session. The browser never supplies the stored name, cover, year, or platform name: library writes load and validate those values from IGDB using submitted IDs. Challenge creation snapshots the name and cover from the recipient's saved game. Challenges are keyed to the IGDB game, so a game saved on several platforms shows the same challenge list on each copy. Game and player search load separately so one source can still display results if the other fails. A fallback account display label uses the part before `@` rather than returning an email address in player search or profiles.

## External data and storage

`lib/igdb.ts` gets a Twitch client-credentials token using `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET`, caches it in server memory until near expiry, and calls the IGDB games and platforms APIs. The platform catalog is cached in server memory for 24 hours. Game search applies an optional list of platform IDs in IGDB before its 30-result limit; the parenthesized IGDB filter returns games available on any selected platform. It converts IGDB image IDs into image URLs and release timestamps into UTC dates and years. Search fetches compact cards; the game detail endpoint fetches richer metadata. Credentials stay server-side. Search results are transient; saved records hold a snapshot of basic IGDB details, so they do not update automatically when IGDB changes.

`db/schema.ts` defines `library_items`, `accounts`, `account_roles`, `sessions`, `login_attempts`, `auth_tokens`, `friendships`, `challenges`, `game_favorites`, `game_ratings`, and `messages` in SQLite/D1. Account emails are normalized to lowercase for friend-request lookup, display names are unique among email accounts under SQLite ASCII case folding, and public visibility defaults to false. A friendship row stores an ordered user pair, the requester, and `pending` or `accepted` status. A challenge is keyed to recipient and IGDB game rather than to a removable library row. Its game snapshot keeps historical entries readable after removal; if the game is saved again, its challenge list reappears. Challenge lists are single SQL statements (`lib/challenge-queries.ts`) that join both players' accounts and take the cover from the newest library copy of the linked IGDB game that has one, then the challenge's saved cover snapshot; received lists leave out declined challenges in SQL; when both are missing, challenge lists attempt the same IGDB artwork recovery used for legacy profile covers. The challenge is completed only while both confirmation flags are true. Either participant can undo their own confirmation. The nullable `timeline_at` stores the time of the latest visible state transition, updated atomically with confirmation flags; creator-only confirmation, favorites, ranking, and repeated no-op confirmations leave it unchanged. New challenges initialize it to creation time; pre-migration challenges remain excluded until a visible transition. Older records with a recipient decline timestamp remain visible to the creator under Declined for compatibility; new challenges have no decline action, and the challenged player or an admin can permanently remove a challenge. Challenges store a title and description; profile cards omit the description, and their detail dialog displays it on demand. The library stores one entry per IGDB game and selected platform; `platforms_json` remains catalog metadata. A nullable `playing_since` marks a copy as currently playing; see [Currently playing](#currently-playing). A nullable `completed_at` marks a copy completed, and `game_ratings` stores one score per player and game; see [Completed games and scores](#completed-games-and-scores). Indexes on `added_at` and `(igdb_id, added_at)` support the bounded popular games read; per-player indexes on `(user_id, added_at)`, `(user_id, rated_at)`, and the non-null `playing_since` and `completed_at` marks support the friends timeline. Existing rows migrated from the earlier one-game model have platform ID `0` and can be edited to a listed IGDB platform. `db/index.ts` obtains the `DB` Cloudflare binding and creates a Drizzle client. Drizzle migrations live in `drizzle/`; `npm run db:migrate` uses Wrangler to apply pending local migrations and record filenames and timestamps in `d1_migrations`. Existing manually migrated local databases require an explicitly confirmed baseline; see [development](development.md#adopt-an-existing-local-database). Sites manages a separate hosted migration ledger during deployment. `.openai/hosting.json` declares the D1 binding name, while `vite.config.ts` supplies a local D1 binding for development.

## Currently playing

Currently playing is a mark on a saved platform copy, not a separate record: `library_items.playing_since` holds the time the copy was marked. Only an owned copy can be marked, because the mark lives on its library row, and deleting the copy removes it. There is no limit. The same game can be playing on several platforms, and each copy is marked separately. Marking is one conditional `UPDATE` in `lib/currently-playing-queries.ts` that keeps an existing timestamp, so a repeated request never bumps activity. Changing a copy's platform keeps its mark and timestamp.

Library cards have a play toggle, and the shared game details dialog shows a **Playing** toggle beside each owned platform wherever the parent passes `onPlaying` (library, search, timeline, other players' libraries, and both profile sections). `app/currently-playing.tsx` renders the section above the Top 10 on both profile routes, newest first: four latest covers on desktop and three at narrow widths (the stylesheet hides the fourth), with a **Show all** disclosure for the rest. Visitors do not see the section when it is empty. While the row has room, owners get a dashed plus spot that opens `app/game-picker.tsx` with a source over `GET /api/library/copies`. The picker is a native dialog shared with the Top 10: it takes a `PickerSource` (a module-level constant, so its search effect stays stable), waits 250 ms after typing before searching, aborts each previous request, keeps current results in place until new ones arrive, and appends **Load more** pages when the source returns a cursor. Its platform filter is `app/platform-filter.tsx`, the same searchable checkbox dropdown the search page uses; inside the picker, Escape closes the dropdown before the dialog. Toggling a copy calls the playing API and replaces the section's list with the response, without a page reload. **Edit** reveals a remove button on each cover through the same `hasPermission` rule as favorites, and there is no reordering. Profiles read the list only after the existing visibility check.

Each marked copy of a verified accepted friend enters the timeline as its own “started playing” entry, ordered by `playing_since`. Unmarking or removing the copy removes the entry, and marking it again creates a new timestamp. See [timeline behavior](timeline-design.md#currently-playing).

## Favorite games

`game_favorites` stores one independent snapshot per `(user_id, igdb_id)`, including title, cover, release year, `favorited_at`, and `sort_order`. Each player can have at most ten. An atomic conditional insert checks the count and appends the order in the same statement, including concurrent requests. Duplicate adds are idempotent and preserve the timestamp and rank. Games need not be saved in the library; removing a platform copy does not remove a favorite. Unfavoriting removes its current timeline entry; favoriting it again creates a new timestamp and appends it to the list.

The shared game details dialog offers a labeled star toggle with loading, limit, and error feedback. Both profile routes display favorites as the Top 10 directly below the nameplate, in saved order: covers on two shelves of five. Each cover is a button whose accessible name carries its rank, title, and year; a caption under the shelves repeats them for the hovered or focused cover and is hidden from assistive technology. On My profile, the next empty spot opens `app/game-picker.tsx` with a source that starts on the viewer's library (`/api/library/copies?group=game`, ten games per page, labeled “Your library”) and switches to `/api/igdb/search` once the search has two characters (IGDB's minimum), returning one page of up to 30 games labeled “All games on IGDB”. Library platform IDs are IGDB platform IDs, so one `/api/igdb/platforms` list, fetched once per page view, filters both. Rows toggle favorites through the favorites API and replace the shelf's state with the response. Adding is disabled with a note once ten are saved; removing still works. An **Edit** toggle turns covers into pick-up and put-down controls (click, Enter, or drag) and reveals a labeled remove button on each; Escape puts a held cover back, and a visually hidden status region announces each move. Moves update the order optimistically, then replace it with the server response or roll back on error. Admin viewers can rank and remove another player's favorites through the same controls, using `hasPermission`; opening that player's game details still manages the viewer's own favorites and library. Profiles read favorites only after the existing visibility check. No role or owner email is serialized with a favorite.

| Route | Behavior |
| --- | --- |
| `GET /api/game-favorites` | Signed-in viewer's own ordered favorites; private, uncached response. |
| `POST /api/game-favorites` | Same-origin, signed-in write accepting `{ igdbId }`; validates catalog metadata against IGDB, adds for the viewer only, returns 409 when all ten slots are occupied. Repeated adds are idempotent. |
| `PATCH /api/game-favorites/:id` | Same-origin write accepting `{ position: 1–10 }`; owner or admin only. Atomically moves the favorite to that position against current database order and shifts the favorites in between one place, without updating the favorite timestamp. Positions past the last favorite clamp to the end. |
| `DELETE /api/game-favorites/:id` | Same-origin write; owner or admin only. Removes the favorite and frees a slot. |

Favorites enter the existing friend timeline as separate “favorited a game” entries, sorted by `favorited_at` alongside library batches and challenges under the shared page size. Only verified accepted friends qualify, including private friends. A stranger's public profile or an admin role does not subscribe their favorites to the viewer's timeline. Favorite cover/title rows open the shared game details dialog. Reordering never changes activity recency.

## Completed games and scores

Completed is a mark on a saved platform copy: `library_items.completed_at` holds the time it was marked, set by one conditional `UPDATE` in `lib/completion-queries.ts` that keeps an existing timestamp. It is independent of `playing_since`, so completing a game leaves it in Currently playing. Library cards have a completed toggle beside the play toggle, and the pressed toggles alone show both marks; other players’ library cards, which have no toggles, show a green “Completed” line; on both profile routes each Currently playing cover has a small corner mark that owners (or admins, through `hasPermission`) toggle, and visitors see only when the copy is completed.

`game_ratings` stores one 1–5 score per `(user_id, igdb_id)` with a snapshot of the title, cover, and release year loaded from IGDB, like favorites. Any game can be scored, owned or not. The shared game details dialog shows five stars for signed-in viewers (`app/game-rating.tsx`): clicking a star sets the score and clicking the current score clears it. A rescore updates only `score`, keeping `rated_at`. Library responses and profile libraries join the owner's score for each copy's game (`getLibraryGames` in `lib/social.ts`), and cards show it as read-only stars. Scores are the viewer's own only; there is no route for changing another player's score.

| Route | Behavior |
| --- | --- |
| `GET /api/game-ratings/:igdbId` | Signed-in viewer's `{ score }` for that game, or `null`; private, uncached response. |
| `PUT /api/game-ratings/:igdbId` | Same-origin, signed-in write accepting `{ score: 1–5 }`. Creates the rating from fresh IGDB data or changes the existing score. Returns `{ score }`. |
| `DELETE /api/game-ratings/:igdbId` | Same-origin, signed-in write that clears the viewer's score. |

Completed copies and scores enter the friend timeline; see [timeline behavior](timeline-design.md#completed-games).

## Messages

Players can send direct messages to accepted friends. There is one conversation per pair of players, stored as rows of `messages` keyed by the ordered pair (`user_low`, `user_high`, like `friendships`) with the sender, recipient, a plain-text body of 1–2000 characters (trimmed; counted in characters, as SQLite `length()` counts them), `created_at`, and `read_at`. The autoincrement `id` orders a conversation and is its paging cursor. Messages are never emailed, never enter the friends timeline, and have no edit, delete, attachment, typing, or read-receipt features.

Messaging requires a verified accepted friendship at the moment of each read or write, for admins too (see [Roles and permissions](#roles-and-permissions)). The send is one `INSERT … SELECT … WHERE EXISTS` statement that checks the friendship and both accounts' verification, so a message cannot land after an unfriend. Removing a friendship hides the conversation and blocks sending; the history stays, and reappears if the players become friends again. Deleting an account deletes its messages.

`/messages` (`app/messages/page.tsx`) and `/messages/:displayName` (`app/messages/[name]/page.tsx`, using the same URL segment as the friend's profile, including the ID fallback for legacy accounts) share `app/messages/messages-page.tsx`. It reads the conversation list and, when a friend is named, that conversation's newest 30 messages; a name that is not a current friend returns 404. `app/messages/messages.tsx` renders friends on the left, most recent conversation first and then friends without messages by name, each with a 140-character preview and an unread count, under a search field that filters the loaded list by display name as you type (Escape clears it); selecting one loads its conversation on the right and updates the URL with `history.pushState`, so Back and direct links work. Scrolling to the top of a conversation (or its **Load older messages** button) loads the previous 30 by `before=<oldest id>` and keeps the reading position. At 720px and below only one pane shows at a time.

There is no push delivery. While the messages page is visible it polls `GET /api/messages` every 10 seconds (and on returning to the tab); only when the open conversation's latest message is newer than the last one it synced does it fetch `after=<id>`, append the new messages, announce them through a polite live region, and mark them read. Opening a conversation marks read only messages up to the newest one loaded. Every signed-in header reads `GET /api/messages/unread-count` on load, when the tab becomes visible, and every 60 seconds while visible; the messages page also passes fresh counts to the header through a `messages-changed` window event. Unread counts include only current verified friends, so the badge never points at a hidden conversation. A partial index over unread rows keeps these counts cheap, and the conversation list costs two index lookups per friend.

| Route | Behavior |
| --- | --- |
| `GET /api/messages` | The signed-in player's verified accepted friends, each with `userId`, display `name`, `profileHref`, `href` (their `/messages/…` path), and the latest message's `lastId`, 140-character `lastBody`, `lastMine`, `lastAt`, plus `unread`. Private, uncached response. |
| `GET /api/messages/unread-count` | `{ count }` of unread messages from current friends. Private, uncached response. |
| `GET /api/messages/:userId` | `{ messages, more }`: the newest 30 messages oldest first, each `{ id, mine, body, createdAt }`. `before=<id>` returns the 30 before that ID; `after=<id>` returns up to 100 newer ones for polling (`more` is always false). Malformed or combined cursors return 400; a non-friend returns 403. Private, uncached response. |
| `POST /api/messages/:userId` | Accept `{ body }`, send it, and return `{ message }`. Returns 400 for an empty or too-long body and 403 unless the two are verified accepted friends. Requires sign-in and same-origin write. |
| `PUT /api/messages/:userId/read` | Accept `{ upTo: id }`, mark that friend's messages to the viewer up to that ID read, and return the viewer's remaining unread `{ count }`. Requires sign-in and same-origin write. |

Accepted friends' profiles show a **Message** button linking to the conversation.


## Xbox connection, played games, and achievements

`/settings/xbox`, linked from Connected libraries, connects an Xbox profile to an existing verified RGBoner account through Microsoft sign-in (OAuth 2.0 authorization code with PKCE on the `consumers` tenant, scope `XboxLive.signin offline_access`). Email login and sessions remain the sign-in method. The callback exchanges the code with the server-only `XBOX_CLIENT_ID` and `XBOX_CLIENT_SECRET`, trades the Microsoft access token for an Xbox Live user token and an XSTS token, and takes the XUID and gamertag from the signed XSTS claims; it never accepts a pasted gamertag. One Xbox profile can belong to only one RGBoner account at a time. The rotating Microsoft refresh token and the cached XSTS token are stored only as AES-GCM ciphertext under `XBOX_TOKEN_KEY` (`lib/token-crypto.ts`), bound to the connection ID, and are never sent to the browser or logged. Missing configuration disables connecting and refreshing; existing added copies keep working.

`lib/xbox-api.ts` holds the HTTP boundary and parsers: title history from `titlehub.xboxlive.com` (games only, with devices, last played time, Store product ID, and achievement and Gamerscore totals) and achievement lists from `achievements.xboxlive.com` (contract 2 for modern titles with continuation pages, contract 1 definitions plus earned lists for Xbox 360 titles). Requests use manual redirects and 15-second timeouts; 401, 429, and other failures map to player-facing errors without changing saved games.

Refresh is manual and limited to one attempt every five minutes. It records every played game; the list is ordered by last played time, so the top of the page is the player's recent activity. Matching and achievement reads run automatically in background batches while the page is open, paused or resumed by a pause flag saved on the connection (`xbox_connections.sync_paused`, `0020_known_rhodey.sql`) so it survives leaving or reloading the page, as in the [integration sync workflow](integration-sync.md), and, like Steam, never disable the page or overwrite a view the player has since changed. **Add all** is enabled only once both finish. **Remove all games** (`remove-library`, under the connection lease) deletes only the library copies Xbox added or linked, keeps ratings and favorites, and the games become ready to add again, one at a time or with Add all, since Xbox never adds anything on its own; it needs a confirmation, is always available, and opening it pauses sync and cancels an Add all in progress. Matching uses batches of 40: `getXboxCatalogMatches` in `lib/igdb.ts` looks up IGDB `external_games` by Store product ID (Microsoft and Xbox Game Pass sources) or by the Xbox 360 marketplace ID derived from the title ID, then falls back to an exact title match (ignoring trademark symbols) on Xbox Series X|S, Xbox One, Xbox 360, or Windows. Only a single candidate is selected; misses and ambiguous editions show **No match** with a **Find match** action that reuses `app/game-picker.tsx`. Shared results are cached in `xbox_mappings` for seven days.

Nothing is added to the library automatically. Each ready card has **Add** and **Add as playing**; **Add all** adds every ready game in batches of 30, and the finish message reports the number actually added. Choosing a picker result matches and adds in one action. The platform defaults to an existing supported copy, then the newest platform the player actually used, then the newest listed (Xbox Series X|S, Xbox One, Xbox 360, Windows). The match, library copy, link, and optional currently playing mark are written in one D1 batch. An existing `(user_id, igdb_id, platform_id)` copy is linked without changing its metadata, added time, or marks. Removing a copy clears its link; Add all skips it afterward, but a single Add restores it. Added cards show a **Playing** toggle that uses the library's own currently playing endpoint; cover/title buttons open the shared game dialog.

Achievement lists are read only for added games, five titles per request, while the settings page is open and only when the earned count changed since the last read, keeping well under Xbox's per-user limits. Definitions (name, description, icon, Gamerscore, secret flag, rarity in tenths of a percent) are stored once per title in `xbox_achievements`; each player's unlocks are rows in `xbox_unlocks` that keep their first recorded time. `completed_at` on the title is the final unlock time while every listed achievement is earned. Profiles show an **Xbox achievements** section to anyone who can view the profile: total Gamerscore and completions, then up to 12 added games with progress, most recently played first. Selecting one opens a dialog listing its achievements; unearned secret achievements stay hidden. Disconnect deletes the connection, tokens, titles, and unlocks while keeping added library copies. Achievements appear in the [friends timeline](timeline-design.md#xbox-achievements).

Connection insertion and state consumption run atomically. The callback logs fixed stage labels only. `lib/xbox-queries.ts` holds the tested SQL.

## PlayStation connection, played games, and trophies

`/settings/playstation`, linked from Connected libraries, connects a PSN account to an existing verified RGBoner account. Sony offers no sign-in for other sites, so the player signs in at playstation.com and pastes their NPSSO session token from Sony's `ssocookie` page. `POST /api/psn/connect` sends it once to Sony's authorization endpoint (the PlayStation App's public client, redirect read but never followed), exchanges the code for an access and refresh token, and reads the account ID and online ID from Sony; the NPSSO is never stored or logged. One PSN account can belong to only one RGBoner account at a time. The tokens are stored only as AES-GCM ciphertext under `PSN_TOKEN_KEY`, bound to the connection ID with the shared `lib/token-crypto.ts`, and never sent to the browser. Sony's refresh token lasts about two months. When Sony rejects it, the connection is marked `needs_reconnect`, sync pauses, and the settings page shows a short alert with a Reconnect form; reconnecting must use the same PSN account, keeps the connection ID, and keeps every saved game, trophy, and library copy. Missing configuration disables connecting and refreshing; existing added copies keep working.

`lib/psn-api.ts` holds the HTTP boundary and parsers, using the endpoints the PlayStation App uses on `m.np.playstation.com`: the trophy summary (account ID, trophy level, and earned counts by grade), trophy titles (PS5, PS4, PS3, and PS Vita lists with defined and earned counts), the played-games list (PS4 and PS5 titles with concept ID, art, last played time, and playtime), title-to-trophy-list links, and per-list trophy definitions and earned times. Requests use manual redirects, 15-second timeouts, and bounded paging; 401 asks the player to reconnect, and 403, 429, and other failures map to player-facing errors without changing saved games.

Refresh is manual and limited to one attempt every five minutes. It merges Sony's two lists into one row per trophy list (`mergePsnTitles`). Each played title ID joins the trophy list Sony links it to, otherwise a list with the same name (ignoring trademark symbols and punctuation) on that title's own platform, so a game owned on PS4 and PS5 keeps a separate row for each version with its own playtime and trophies; cards name the platform. A version with no list of its own joins its concept's other list, and playtime is summed with the newest play time kept. Games with no trophy list stay as their own `concept:` row. Sony is asked about at most 100 unlinked title IDs per refresh, five per request, and each title ID is asked about once. When a later refresh links a played-only row to its trophy list, the trophy row takes over that row's match, and its library copy only when the copy is on one of the row's platforms. The list is ordered by last played time. Matching, Add, Add as playing, **Add all**, the saved pause flag (`psn_connections.sync_paused`), and **Remove all games** behave exactly like Xbox and follow the [integration sync workflow](integration-sync.md). `getPsnCatalogMatches` in `lib/igdb.ts` looks up IGDB `external_games` from PlayStation sources by Store concept URL or title ID where IGDB records one, then falls back to an exact title match on PlayStation 5, PlayStation 4, PlayStation 3, or PlayStation Vita, preferring the platforms the player used. Results are cached in `psn_mappings` for seven days. The platform defaults to an existing copy on a platform the player used for that version, then the newest such platform, then an existing supported copy, then the newest listed, so a PS4 version never links to a PS5 copy.

Trophy lists are read only for added games, three lists (six requests) per batch, while the settings page is open and only when the earned count changed since the last read. Definitions (name, description, icon, grade, group, hidden flag, rarity in tenths of a percent) are stored once per list in `psn_trophies`; each player's earned trophies are rows in `psn_unlocks` that keep their first recorded time. `completed_at` is the platinum's earned time, or for lists without a platinum the final trophy of the base game; add-on groups never count, so new DLC does not reopen a finished game. Settings cards show earned/total trophies, a Platinum mark, last played, and playtime. Profiles show a **PlayStation trophies** section to anyone who can view the profile: Sony's trophy level and account-wide counts by grade, completions among added games, then up to 12 added games with progress and playtime, most recently played first. Selecting one opens its trophy list; unearned hidden trophies stay hidden. Disconnect deletes the connection, tokens, titles, and earned trophies while keeping added library copies. Trophies appear in the [friends timeline](timeline-design.md#playstation-trophies).

The connect and reconnect forms explain that the NPSSO is a sensitive credential, distinguish it from the encrypted sign-in tokens kept on the server, and describe deletion on disconnect and reconnection after roughly two months or sooner. They disclose that the connection is unofficial and not approved by Sony, that sharing credentials may conflict with Sony’s terms, and that account restrictions cannot be ruled out. Both notes are associated with the token input for assistive technology.

Migration `0021_slippery_skin.sql` adds `psn_connections` (one PSN account per RGBoner account, online ID, encrypted tokens, refresh, pause and reconnect state, trophy level and grade counts, and a short operation lease), `psn_mappings` (shared catalog candidates), `psn_titles` (per-connection merged games keyed by trophy list ID or `concept:` ID, with played title IDs, platforms, playtime, trophy counts by grade, catalog choice, library link, and completion), `psn_trophies` (shared definitions), and `psn_unlocks` (per-player earned times, indexed by player and time). ## RetroAchievements connection, games, and achievements

`/settings/retroachievements`, linked from Connected libraries, connects a RetroAchievements (RA) account to an existing verified RGBoner account. RA's Web API is public and read with the site's own Web API key (`RA_API_KEY`), so no player credential is ever stored. RA has no sign-in for other sites yet, so linking follows RA's own guidance for integrations: the player enters their RA username, `startRaLink` looks the account up and saves a one-time `RGB-` code with the account's permanent ULID in `ra_link_codes` for 15 minutes (a new code at most once a minute), and the player puts the code in their RA motto. **Verify** reads that ULID's profile (at most once every five seconds) and links the account only when the motto contains the code; only the account owner can edit it. The player can then remove the code. The connection keys on the ULID because RA usernames can change; every Refresh saves the current username. One RA account can belong to only one RGBoner account at a time. Without `RA_API_KEY`, connecting and refreshing are disabled; existing added copies keep working.

`lib/ra-api.ts` holds the HTTP boundary and parsers for RA's Web API: the user profile (ULID, username, motto, hardcore, softcore, and RetroPoints), completion progress (every game with progress, 500 per request, up to 10,000 games), user awards (beaten and mastered or completed awards with their mode, and account-wide award counts), recently played games (last played times for the 50 most recent), the extended game record (only to find a subset's main game), and per-game progress (achievement definitions, rarity from distinct players, softcore and hardcore unlock times, and playtime). Requests identify RGBoner with a user agent, use manual redirects and 15-second timeouts, and map 404, 429, a rejected key, and other failures to player-facing errors without changing saved games.

Refresh is manual and limited to one attempt every five minutes. `mergeRaGames` folds every `[Subset - …]` game into its main game, like PlayStation add-on trophy groups: a subset joins the main game with the same base title on the same console, or a main game found earlier, otherwise RA is asked for its parent (up to 20 lookups per refresh; the rest wait for the next refresh). A row's counts cover the main set and its subsets. `completed_at` is the first time the main game was beaten in either softcore or hardcore; a set that cannot be beaten completes when it is mastered or completed, and awards a player hid on RA fall back to the highest award RA reports for the game. Completion keeps its earliest time once set, so a revised set never reopens a beaten game, and `completed_hardcore` records whether it was done in hardcore. Last played is RA's last played time for recent games, otherwise the newest unlock. The list is ordered by last played time. Matching, Add, Add as playing, **Add all**, the saved pause flag (`ra_connections.sync_paused`), and **Remove all games** behave exactly like Xbox and PlayStation and follow the [integration sync workflow](integration-sync.md). IGDB records no RetroAchievements IDs, so `getRaCatalogMatches` in `lib/igdb.ts` matches by exact title or IGDB alternative name on the IGDB platforms mapped from the game's RA console (`raConsolePlatforms` in `lib/ra-types.ts`), trying RA's title variants: without `~Hack~`-style tags, each half of `A | B` titles, a trailing article moved to the front, and without colons. A main-title match wins over alternative names, and only one unique result is selected. Results are cached in `ra_mappings` for seven days. Games RA lists under a console with no IGDB platform, such as Standalone, and games IGDB doesn't have stay unresolved for the player to match. The platform defaults to an existing copy on the game's own console, then that console's usual release, then any existing supported copy.

Achievement lists are read only for added games, three games per batch (one request for the main set and one per subset), while the settings page is open and only when the softcore or hardcore unlock count changed since the last read. Definitions (title, description, badge, points, display order, rarity in tenths of a percent, and the subset's name) are stored once per achievement in `ra_achievements`; each player's unlocks are rows in `ra_unlocks` that keep their first recorded time and gain the hardcore mark if the achievement is later earned in hardcore. Playtime is the longest of the main set's and its subsets' totals, because they share play sessions. Settings cards show the console, earned/total achievements, Beaten (and Hardcore), last played, and playtime. Profiles show a **RetroAchievements** section to anyone who can view the profile: the account-wide number of games beaten, then up to 12 added games with progress, Beaten or Beaten · Hardcore, and playtime, most recently played first. Points, RetroPoints, and mastery and completion counts are stored for later but not shown. Selecting a game opens its achievement list with badges (RA's locked version for unearned ones), points, earned date, Hardcore, rarity, and the subset name. Disconnect deletes the connection, games, and unlocks, and any pending link code, while keeping added library copies. Achievements appear in the [friends timeline](timeline-design.md#retroachievements).

## Steam connection and library import

`/settings/steam`, linked from Connected libraries, connects Steam to an existing verified RGBoner account. Email login and sessions remain the sign-in method. The server uses Steam OpenID 2.0 to verify the SteamID; it never accepts a pasted SteamID as proof of ownership. A Steam account can belong to only one RGBoner account at a time. OpenID grants identity, not access to private Steam game details.

Steam library and activity requests go from `lib/steam-api.ts` to the public `api.steampowered.com` endpoint with the server-only `STEAM_API_KEY`. HTTP 401/403 responses identify a rejected site API key; rate limits and other upstream failures retain separate messages, without exposing the key or Steam’s response body. Game details must be visible to the API. Played free games are included. Unknown playtime stays null, distinct from zero. Empty responses without an explicit zero count, malformed responses, truncated lists, and libraries above the supported 10,000-game import limit fail without removing RGBoner copies. Missing games in a later complete refresh stay in the import preview as unavailable; they cannot be imported until reported again. No automatic deletions or background refreshes run.

A library refresh is manual and limited to one attempt every five minutes per connection. The confirmation reports pending matching only when the returned pending count is positive; otherwise it says there are no new games to match. It records lifetime minutes, recent minutes when returned, last-played time when returned, and the observation time. Recent activity is a private snapshot, showing up to ten games, separate from manual `playing_since`. Failed or inaccessible recent-activity responses clear that snapshot; failed library requests also clear it and retain an explicit error. This release does not expose Steam activity on other players' profiles, poll live presence, collect session history, or generate playtime trends.

The preview is paged at 30 games and supports a literal title search with a 250 ms typing debounce and cancellation of stale searches. Catalog matching automatically runs sequential requests of up to 40 pending games while the settings page is open. Progress is saved between batches, and matching can be paused or resumed, and the choice is saved on the connection (`steam_connections.sync_paused`, added by `0019_calm_katie_power.sql`), so a paused sync stays paused after leaving or reloading the page until the player resumes it. A successful library refresh clears the pause. Matching is driven by the open page: leaving it stops scheduling new batches, and returning resumes unless the sync is paused. Background batches never disable the page: they run under a separate syncing state, and every player action (paging, filtering, searching, opening a game, resolving a match) invalidates any batch already in flight so its result cannot overwrite what the player sees. The next batch resumes from the saved progress. **Remove all games** (`remove-library`, under the same lease as other Steam writes) deletes only the library copies this connection imported or linked. Ratings and favorites stay with the game, currently playing and completed marks go with the copies, and `imported_at` stays set so removed games are not imported again. It needs a confirmation and is always available; opening it pauses sync, and the confirmation waits for any matching batch already running, so games added earlier can be cleared at any time. Errors pause matching with a visible retry action. The gallery filters All, Unresolved, Imported, and Recently updated, with IGDB covers and Steam portrait/header artwork fallbacks for games lacking a catalog cover. Manual matching reuses `app/game-picker.tsx`, including debounced search, cancellation, Windows, Mac, Linux, and SteamVR platform filters, intact covers, and Add actions that save the selected match and import its platform copy in a single database batch. Cards distinguish absent catalog identities from identified games without a supported desktop or SteamVR platform; neither is importable. `lib/igdb.ts` looks up Steam's current external source ID, then batches AppIDs through IGDB `external_games`, expanding canonical game metadata. Shared mapping results (including misses and ambiguous results) are cached for seven days. Only one unique IGDB result is selected automatically. Ambiguous or missing matches can be resolved by the player using IGDB search; the server reloads the chosen IGDB game by ID. User choices never modify the shared mapping cache. Unresolved games remain visible without entering the library; the interface has no exclusion control. Legacy exclusion flags remain stored, and setting a match clears them.

Sync never adds games on its own. Eligible catalog matches wait as ready, and **Import all games** appears in the summary panel once matching finishes. Selecting a catalog result resolves and imports an unmatched game in one action. Platform defaults preserve an existing supported copy, otherwise prefer SteamVR when listed for the game, then Windows, Mac, and Linux. Oculus, standalone headsets, and console VR platforms are not enabled for Steam imports. Steam is an ownership source, not an IGDB platform. An exact `(user_id, igdb_id, platform_id)` collision attaches to the existing library copy without changing its metadata, original addition time, playing/completed marks, ratings, or favorites. Otherwise the server inserts a canonical IGDB snapshot at import time. Multiple Steam apps may reference the same RGBoner copy. Removing an imported copy clears its source link but retains the import record; refreshing does not recreate it. Reimport requires another explicit Add action. Existing library platform edits continue to operate on the linked copy.

Automatic sync only runs matching requests, until all games are matched or sync is paused. **Import all games** then runs import batches of up to 30 until every ready game is added, keeping the active filter, search, and page. Each import request pins the verified Steam account and refresh timestamp, and a connection lease prevents overlapping writes. Missing or ambiguous matches remain unresolved. Bulk import skips excluded/unavailable games and previously imported games whose RGBoner copies were removed; restoring a removed copy remains explicit. Errors pause sync with a resume action. Leaving the page stops scheduling new matching requests, and returning resumes saved work unless the sync is paused. Cover/title buttons open the shared game-details dialog for platform management, ratings, favorites, and playing status. Sync and resolution preserve the active filter, search, and page.

New copies participate in the existing friends timeline library batches. Linking an existing copy, mapping, refreshing, exclusions, and playtime updates do not bump its `added_at`. Disconnect deletes the connection, pending linking state, and personal Steam records, while preserving imported RGBoner library copies and their progress. Shared catalog mappings contain no player data and remain cached.

**Recently updated** shows linked Steam games with a recorded library update, newest first, using 30-row pages and the same game popup. `library_items.updated_at` records additions/imports and platform changes; adding a platform copy also updates that game's existing copies. Repeated identical platform edits and routine Steam playtime refreshes do not bump it. Existing rows start null, so applying the migration does not make the whole old import appear newly changed; historical platform edits cannot be reconstructed. The read starts from `(user_id, updated_at, id)` and looks up sources by `(connection_id, library_item_id, app_id)`, with no full catalog JSON scan or temporary ordering table. It does not alter timeline timestamps.

### Steam storage and request safety

Migration `0017_moaning_psylocke.sql` adds nullable library `updated_at` and the two indexes used by Recently updated. Migration `0016_workable_millenium_guard.sql` adds:

- `steam_connections`: one verified SteamID per account, a unique connection generation, refresh timestamps, error state, private recent snapshot, and a short operation lease.
- `steam_link_states`: a hashed random linking state, exact return URL, and ten-minute expiry, bound to the signed-in account. New linking attempts are limited to one per minute. The stored return URL also contains the raw random state needed for exact OpenID verification; this short-lived record is private and never logged.
- `steam_mappings`: AppID-keyed canonical catalog candidates and cache timestamps, independent of players.
- `steam_games`: one personal source record per connection/AppID, metrics, observation time, catalog choice, exclusion flag, import time, and nullable library-copy reference.

SteamIDs are strings to avoid JavaScript integer precision loss. API responses are private/no-store. Authenticated Steam APIs are scoped to the current account through `hasPermission`; no request accepts another player's account ID. Writes require an explicit same-origin Origin header. OpenID is the intentional callback exception: it validates the provider, identity namespace, signed fields, exact return URL, fresh nonce, duplicate parameters, and signature directly against Steam's pinned HTTPS endpoint. Steam HTTP requests use manual redirect handling supported by the Worker runtime and reject non-success responses without following redirects. Connection insertion and state consumption run atomically; expired, replayed, or disconnected flows cannot insert a link. Callback redirects carry only a fixed status code, with no-referrer and no-store headers. Only a successful connection uses a success banner; failed, expired, unavailable, or cancelled linking uses an alert. Verification diagnostics log fixed failure-stage labels only, never identities, callback URLs, signatures, or state tokens.

Long-running operations acquire a D1 lease and carry a unique connection generation and operation token. Disconnect/relink invalidates in-flight work. Library inserts and source attachment use a D1 batch transaction and uniqueness constraints. Partial source refresh failures can leave newly observed source rows, but never delete or edit RGBoner copies; unavailable rows cannot be imported until a successful complete refresh. `lib/steam-queries.ts` holds the tested atomic SQL.

| Endpoint | Behavior |
| --- | --- |
| `GET /api/steam?page=0&search=…&view=all` | Current player's connection, recent snapshot, counts, and paged preview. |
| `POST /api/steam/connect` | Start a verified account-link flow and return Steam's login URL. |
| `GET /api/steam/callback` | Verify Steam's assertion, atomically link, and redirect to settings. |
| `POST /api/steam` | Validated `refresh`, `match`, `choose`, `ignore`, `import`, `import-matched`, `resolve`, `pause` (a saved `paused` boolean), `remove-library`, or `disconnect` action; returns refreshed preview state. |
